# 两屏切换检查：2026-10-29

检查对象：Glass Start 5.4.1，初轮基于 Git `7ac5dd830060ccaa456364417b7b0a234d15a252`。初轮未修改应用源码；后续记录三处最小修复及各自复测。

当前评估：预热后的连续切换和同进程前台新标签页复核平稳，未发现切屏卡死、状态锁不释放或手势失效；首次绘制及启动压力下仍有慢帧。已修复三处可避免的布局读取/样式重算，没有宣称首次渲染尖峰已经根治，最初 83.3ms 样本的原因也未能唯一还原。以下各阶段的结果分别列出，不能将不同启动条件混合比较。

- Chrome 156.0.8078.48，无头模式，本地生产构建，不注入应用测试接口；网页性能采样绕过 Service Worker。

## 状态与实现检查

- `screen-state.js` 各入口共享过渡锁，动画期间不会反转或排队；正常结束、减弱动效、事件丢失的计时兜底及唤醒清理均有回归覆盖。
- 往返复用导航 DOM；目录未变化时 `renderNavCategories()` 返回缓存。前 5 类图标先准备，其余图标延后至空闲调度，避免全部加载集中在切屏首帧。
- Chrome 保留离屏合成提示和毛玻璃结构；离屏内容仍由 `inert`、无障碍状态和指针规则隔离。
- 两种模式的移动 CDP 触摸均可进入、返回；各性能矩阵会话最后均已解锁，首屏可交互、导航屏 inert，无未捕获 JavaScript 异常。
- 96 次矩阵与移动复测切屏的观察窗口中，`PerformanceObserver` 未记录超过 50ms 的主线程长任务。此结论不覆盖 GPU 停顿，也不排除小于 50ms 的耗时任务。
- 移动复测各会话 DOM 数量从 1392 一次增至 1475，后续往返保持 1475，没有逐轮增长。未进行堆快照或长时间内存泄漏测试。

## 继续追查：Trace 与最小修复

用户要求继续检查后，对移动 sheet 模式增加 8 个全新会话的原速 Trace。16 次切换均未出现慢间隔，最大 rAF 间隔 16.8ms；切屏窗口主线程任务最大 20.127ms，Layout 最大 0.371ms，没有超过 50ms 的长任务或长动画帧。Trace 覆盖页面加载、首次进入及首次返回，启用主线程、渲染、光栅化与合成相关分类，保存在本地忽略目录 `test/artifacts/transition-mobile-trace-*.json`。

随后用 4 倍 CPU 降速的 4 个新会话抓取 Trace：4 次首次返回均在第一个采样间隔出现 31.3–32.4ms，能够重复观察。返回的同一个主线程任务内先后出现两次大范围样式重算，任务总耗时为 32.668–45.529ms。

额外的 2 个会话对 `HTMLElement.prototype.blur/focus` 加入计时包装，确认返回时 `navContent.blur()` 分别耗时 13.6ms、9.3ms。第一份 Trace 中，该调用附近对应一次 1178 个节点、13.471ms 的 `UpdateLayoutTree`，其后另有 1294 个节点、19.881ms 的目标状态样式重算。根因是 `prepareScreenTransition()` 先添加 `is-screen-transitioning`，再调用 `blur()`，同步提交了已经弄脏的样式。

修复仅将失焦操作移到切屏样式修改之前，保留原有切屏状态与输入规则，没有增加定时器、状态或抽象。复用既有手势、焦点、动画锁和减弱动效回归，不新增顺序断言测试。

同条件再测 4 个全新会话，结果如下。修复前 4 次为无焦点包装的压力 Trace，修复后 4 次含焦点计时包装；属于顺序执行的小样本对照，不是严格随机实验。

| 指标：首次返回，移动 sheet、4 倍 CPU 降速 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 返回按键 EventDispatch 耗时 | 11.678–15.038ms | 1.010–1.420ms |
| `blur()` 耗时（独立包装会话） | 9.3ms、13.6ms | 4 次均低于计时精度，显示 0ms |

| 首个 rAF 采样间隔 | 31.3–32.4ms | 不超过 16.8ms |
| 4 次返回的慢间隔数量 | 4 | 0 |

修复后的原速桌面评测也完成首次及 5 轮往返，共 12 次切屏：各组 P95 为 16.7–16.8ms，最大间隔 16.8ms，无慢间隔。主线程任务耗时与 rAF 间隔是不同指标，不能互相换算成物理屏幕漏帧数量。

## 再次追查：启动竞争与连续往返

本阶段继续使用上述失焦顺序修复后的代码，没有再修改应用源码。增加启动条件对照及连续往返，避免只重复“加载完成后”的同一种测试。每个启动会话使用新 Chrome 配置并记录 Trace；仅保留达到阈值的完整 Trace，其余保留汇总。条件仍为移动视口 390×844、DPR 3、sheet 动画。

| 启动条件 | 新会话数 | 两个方向合计慢间隔数 | 最大 rAF 间隔 |
| :--- | ---: | ---: | ---: |
| 等待字体和 30 个空闲帧 | 6 | 1 | 33.4ms |
| 刻意在启动清理计时器到期前约 180ms 进入 | 4 | 0 | 16.8ms |

最后一项是更强的启动压力条件，不可与先前“等待页面及字体就绪、采样空闲帧后再切屏”的降速结果混为一谈。4 个会话的首次进入最大间隔分别为 40.7ms、550.0ms、283.4ms、113.2ms；因此启动压力下确实存在明显卡顿，不能继续用“所有切屏都平稳”概括。

### 抓到的耗时来源

1. 启动 800ms 后移除 `.fade-in` 的任务，在 4 次刻意碰撞中耗时最多约 0.1ms，没有慢间隔；本轮不支持将原始尖峰归因于这个清理任务。
2. 慢网络另补 2 个新会话并保存详细 Trace，最大间隔分别约 33.4ms、50.0ms。主线程的 `LayerTreeHost::WaitForCommitCompletion` 分别占用 26.47ms、33.85ms；切入按键本身仅约 7.77ms、6.13ms。捕获到的是等待合成提交，不是同等时长的业务 JavaScript 执行。
3. 550ms 的启动压力样本中，GPU 线程 `RasterDecoderImpl::DoEndRasterCHROMIUM` 耗时 574.74ms，同时有一个 `DawnPlatformImpl::RunWorkerTask` 耗时 571.19ms。主线程的 Chrome 图层销毁任务 `LayerTreeHost::~LayerTreeHost` 内，`ProxyMain::Stop` 等待 506.76ms；其上层任务来源为 `widget_base.cc` 的 `Shutdown`。这解释了本次捕获的最大停顿，但 Trace 未细分 Dawn 工作任务的具体内部操作，不能进一步断言是哪种着色器编译。
4. 更早的首帧还存在应用侧成本：目录未在空闲时间准备好时，进入按键内出现目录 HTML 解析、样式重算和布局；3 份详细压力 Trace 中，按键事件分别耗时 65.2ms、73.1ms、73.8ms。它与后续浏览器图层等待是两种不同的开销，不能把启动慢帧全部归给 GPU。

### 浏览器启动路径对照

- 关闭 Skia Graphite 的 4 个压力会话，最大进入间隔为 66.7ms、88.6ms、70.1ms、81.0ms。但 `SystemInfo.getInfo` 同时报告 GPU 合成和光栅化退回 `disabled_software`；因此这是软件渲染对照，不能单独证明 Graphite 有缺陷，也没有将该开关写入产品配置。
- 另做 4 个会话：先导航到同源空白页，等待 1300ms，再导航到应用并立即切入，仍保留 4 倍 CPU 降速。最大间隔为 64.9ms、66.7ms、56.0ms、49.9ms；`ProxyMain::Stop` 最大仅 0.068–0.741ms，Dawn 工作任务最大为 3.394–4.105ms。数百毫秒级等待没有再出现，支持它与浏览器启动/页面导航阶段的渲染初始化及清理有关。这个对照也预热了渲染进程，且首次目录准备时机有所不同，不能据此把全部差异只归给某一个浏览器函数。

这些压力 Trace 提供了实际抓到的慢帧来源；最初那次 83.3ms 没有当次 Trace，仍无法追溯为上述任一来源。没有通过删减毛玻璃效果、增加状态或改动启动流程来掩盖尚未充分隔离的问题。

## 进一步评估：首次目录构建的同步读取

重新检查当前源码后，对 `scrollTop`、布局尺寸、`innerHTML`、`inert`、`focus/blur` 等原生调用加上临时计时包装，同时记录触发前目录是否已经生成。包装只用于诊断会话，没有进入应用源码。3 个原速快速切入及 4 个 CPU 降速快速切入会话显示：目录尚未构建时，`renderNavCategories()` 会在切屏样式已经改变后读取空目录的滚动位置。4 倍 CPU 降速会话中，这次额外同步读取耗时约 4.2–6.0ms；后续目录构建和聚焦仍需另行计算布局。

第二处最小修复位于 `modules/bookmarks.js`：目录为空时使用初始滚动位置 0；已有分类节点时才读取并保留当前位置。导航内容区只包含分类容器，因此空目录没有需要恢复的内容滚动位置。没有添加缓存状态、延时调度或改变键盘焦点规则。

修复后再做 4 个同条件新会话，均确认进入前目录为空：切屏起始 100ms 内不再出现超过 2ms 的 `scrollTop` 读取，原先每会话的额外 4–6ms 读取消失。进入事件耗时从对照组的 57.1–69.1ms 变为 45.0–57.4ms，但首次帧间隔仍可达 83.4–116.7ms。样本量小且启动负载有波动，不能把整个事件时长差异或帧间隔变化都归于这一行代码，也不能据此宣称冷启动卡顿已消失。

另以滚轮触发做 4 个降速快速切入会话，事件耗时为 13.3–21.0ms，没有导航聚焦调用，但首次间隔仍达 82.2–94.2ms。部分样式和布局工作从键盘处理内转移到浏览器渲染阶段；这说明只延后键盘焦点不能消除首次渲染成本，未引入异步焦点或额外过渡状态。

在既有 `ui-sidebar-cache.test.mjs` 中补充用户行为断言：重建非空目录后保持当前滚动位置。最新改动的 `npm run lint`、`npm test -- ui-deferred-nav-icons`、`npm test -- ui-sidebar-cache`、`npm test -- infra-chrome-extension` 均通过；浏览器测试入口已执行类型检查和对应构建。最新扩展产物的 sheet、classic 各补测 6 次切换，共 12 次，最大间隔 16.8ms，无慢间隔、异常或切屏锁残留。完整报告的初轮压力数据仍保留为历史测量，不冒充最新版本的结果。

最新原生调用诊断与对照汇总保存在 `test/artifacts/transition-cold-evaluation-summary-2026-10-29.json`，原始结果为同目录中的 `transition-startup-native-calls-2026-10-29.json`、`transition-startup-empty-fix-2026-10-29.json`、`transition-startup-wheel-cold-2026-10-29.json`。本轮不涉及发布，未运行全量测试和 W3C 校验。

### 可见 Chrome 与 GPU 进程复用

随后使用独立临时配置的可见 Chrome 窗口复核，不再仅依赖无头模式：

- 原速的 3 个首次进入样本，最大间隔分别约 249.8ms、17.6ms、17.5ms。第一个样本同时捕获到超过 200ms 的 Dawn 工作任务和 GPU 光栅化任务，主线程最大任务仅约 19.4ms。该组未逐帧记录焦点，部分会话结束时窗口未获焦点；因此不能将 249.8ms 直接当作已确认的前台呈现帧率。
- 4 倍 CPU 降速立即进入的 4 个可见窗口样本，最大间隔约 83.8–166.7ms，保留为启动压力证据。
- 另对 2 个可见 Chrome 会话进行 `/usr/bin/sample` GPU 进程线程采样，均成功完成。样本中出现 `newLibraryWithSource`、`MTLLibraryBuilder`、`AGX::Compiler::compileProgram` 等调用，支持 Metal 库/管线创建参与首次绘制的判断；不支持将整段停顿全部量化为编译时间。原生线程采样本身有开销，这两次运行不作为无干扰性能基准。
- 最后使用 3 个新 Chrome 进程，每个进程依次测试首个应用标签页、新应用标签页、清除资源缓存后再开的应用标签页，共 9 个页面、18 次切换。逐帧确认进入采样全部获焦点；整体最大间隔约 17.8ms，无慢间隔。后续新页的 Dawn 工作任务最大约 0–0.7ms。即使清除资源缓存也没有复现长停顿，说明不能简单把图片缓存缺失当作主要原因。该对照没有清除操作系统或驱动缓存，也不能单独断言 Chrome 或 Graphite 存在某个确定缺陷。

这些结果把剩余风险收敛到首次绘制/浏览器渲染初始化路径，仍未对应到最初缺少 Trace 的 83.3ms 样本。不引入隐藏画布预热、额外绘制层或浏览器功能开关作为应用补丁。

### 后台恢复中发现的第三处同步计算

在可见 Chrome 中，让切屏进行时切到另一个标签页，分别等待 100ms、1000ms 再返回；覆盖 sheet、classic、两个方向、原速及 4 倍 CPU 降速，共 16 个场景。恢复目标、过渡锁与 inert 状态全部正确，但一次降速恢复同步处理达 73.5ms，不能据状态正确就认定没有性能开销。

继续抓取 8 个降速场景的 Trace 和原生调用计时，确认 `reconcileScreenState()` 原先先清理过渡样式，随后读取 `window.scrollX`，提前同步提交大范围样式重算；之后设置目标屏幕又需计算布局。`scrollX` 读取在若干场景耗时约 10–16ms。两屏的第二次 `offsetHeight` 读取只需约 0–0.8ms，没有为此额外改写布局提交循环。

第三处修复仅将屏幕恢复中的滚动读取放在过渡样式清理之前，复用正常切屏已有的读写顺序；没有增加状态、定时器或改变恢复目标。对照 Trace 中，短暂后台后恢复首屏的结果如下：

| 4 倍 CPU 降速、后台 100ms 后恢复首屏 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| sheet 恢复同步处理 | 31.8ms | 16.7ms |
| classic 恢复同步处理 | 22.9ms | 16.9ms |
| 两组主要样式重算节点数 | 1230 + 1146 | 596 |

这些是单次配对 Trace，不能作为所有唤醒场景的固定提速比例。最新版本另完成 8 个带窗口读取计时的网页场景、8 个 Trace 场景、8 个真实 Chrome 扩展后台恢复场景，均无未捕获异常或过渡锁残留。网页计时组及扩展组还检查了目标屏幕顶部为 0、尺寸匹配视口、根滚动归零、返回首屏后导航滚动归零，全部通过。扩展 8 个场景的恢复同步处理约 2.0–5.2ms。

在恢复后立即用下一次输入切屏的压力条件中，仍捕获到少量约 33–43ms 的间隔，不能宣称所有切换均为零慢帧。新修复针对已确认的重复样式计算，不承诺消除全部浏览器调度和首次绘制等待。
