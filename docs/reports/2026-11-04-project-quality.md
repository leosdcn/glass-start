## 需要处理的问题

### 1. [P2，优先处理] 自动部署未以质量检查成功为前提

依据：`.github/workflows/deploy.yml:3` 与 `:17`；对照 `.github/workflows/ci.yml`。两个工作流各自在 main push 时启动；部署 job 只有安装、构建和上传发布，没有依赖测试结果。即使构建成功但 lint、类型或行为测试失败，仓库内这套部署定义仍允许发布。未查询远程环境保护规则，因此不判断 GitHub 环境是否另有人工审批。

建议：让检查和部署形成显式依赖，并发布同一提交的已验证产物；发布阶段接入 W3C 校验，错误或服务不可用时按现有项目规则处理。无需新增独立质量平台。

### 2. [P2] 天气日出日落提示混用了系统时区与天气地点时区

依据：`src/js/modules/weather.js:306` 使用浏览器本地小时与日出日落字符串比较；请求使用 `timezone=auto`，`src/js/utils/weather-model.js:127` 则去除了日期且未保留响应时区。

Chrome 定点复现：系统时区设为 Asia/Shanghai，时间固定在 `2026-11-04T12:00:00Z`；天气地点 London，提供当日日出 07:00、日落 16:30、明日日出 07:02。此时伦敦为中午，界面却显示“明日日出 07:02”，应显示“今日日落 16:30”。跨时区旅行、系统时区未更新或 IP 定位到其他时区时会触发。该场景由注入天气数据复现，未依赖真实定位接口。

建议：保留天气响应的时区及完整日期时间，让当前时间和太阳事件在同一时间基准下比较；在现有天气模型/浏览器测试中补充跨时区场景。

### 3. [P2，异常数据场景] 合法 JSON 中的错误书签字段类型会中断初始化

依据：`src/js/modules/bookmarks.js:34` 读取元数据后只规范化 URL 键，`:53` 直接使用 `custom.name`，`getFaviconHTML()` 随后调用名称的 `.trim()`；`src/js/init.js:86` 调用 `loadBookmarks()`，后面的全局和设置事件装配尚未执行。

Chrome 复现：将书签 URL 列表设为 `["https://example.com"]`，对应自定义元数据设为 `{name:123,icon:"https://example.com/favicon.ico"}`，调用真实 `loadBookmarks()`，得到 `(e.name || "?").trim is not a function`。因此这类记录在启动读取时也会使初始化提前退出。

这属于合成的本地异常缓存测试；普通编辑和导入已做清洗，本次没有发现正常用户操作会写出该记录，也不将其认定为远程可利用漏洞。

建议：仅在持久化读取边界复用现有字段清洗，丢弃或回退错误记录，避免增加新的状态包装或全局兜底抽象。

## 后续改进项

- **网页脚本信任边界**：`src/js/modules/search.js` 的 Bing/Google JSONP 会把第三方响应作为页面脚本执行；HTML 与 `_headers` 保留 `unsafe-inline`。这是已知设计权衡，未发现本次可利用的注入链。若后续收紧，可先核实服务是否支持网页 CORS，再评估替代 JSONP 及首屏脚本哈希方案；扩展已使用 JSON fetch。
- **大文件导入**：`src/js/modules/settings.js:254` 未限制文件大小或书签数量，读取后同步 JSON.parse、清洗并渲染全部条目。可增加简单的大小/条数上限及提示。本次未进行大文件内存压力实验，不将其列为已复现卡死。
- **验证边界**：视觉脚本是截图与布局断言，不做基准图像差分；现有无障碍检查也不是完整对比度、屏幕阅读器或标准符合性审计。可按实际风险补充重点场景，不必引入庞大框架。
- **性能维护**：核心 HTML 208.24 KB（包含 CSS 91.12 KB）和 JS 142.29 KB，都是未压缩传输编码前体积；静态产物总计约 4.52 MiB，壁纸占约 3.46 MiB。保持当前按需图片策略，未来功能增长时关注 HTML/JS 基线即可，现有证据不支持为拆分而拆分。
