# Glass Start 性能研究

- 基线为 v5.5.6，Git `1c35625`。使用本地生产构建，在 Apple M4 上运行无头 Chrome 157.0.8103.51，启用 GPU 合成。移动场景通过 CDP 模拟。候选实现只用于临时构建与请求对照。
- 下载实验使用本地服务器、冷资源缓存和模拟网络，另用真实安装的 Service Worker 验证离线缓存路径。网页与扩展使用各自的实际构建。外部天气请求隔离。耗时只反映所测环境，未收集线上用户数据。

## 优先顺序

| 顺序 | 候选项 | 已观察到的收益 |
| :--- | :--- | :--- |
| 1 | 停止桌面冷启动时自动下载下一张预设壁纸 | 默认配置少下载 532 kB。限速实验中当前壁纸下载完成中位数提前约 0.82 秒 |
| 2 | 缩减窄屏上导航图标的空闲预取范围 | 390×844 下，额外 PNG 预取从 327 kB 降到 110 kB。第 6.5 秒进入时，19 张可见图标均已加载 |
| 3 | 减少网页首次安装 Service Worker 的核心资源重复下载 | 带 Brotli 和 ETag 的对照中，HTML 与脚本额外传输的 126,801 B 降至 0 B，一次 HTML 304 仍保留 |
| 4 | 为窄幅竖屏提供默认壁纸的高清居中裁切版本 | 单图正文 410 → 206 kB，下载完成中位数 3.75 → 1.77 秒。需接通壁纸恢复与离线缓存 |
| 5 | 降低大图上传时的主线程编码成本 | 4 倍 CPU 降速下，预览前最大 rAF 间隔由 183–267 ms 降到 50–100 ms |
| 6 | 用已有容错阈值限制本地书签模糊匹配计算 | 250 条已保存书签下同步输入处理 P95 为 26.1 → 7.8 ms。默认配置收益约 0.9 ms |

资源体积采用十进制 kB。不同实验的时间收益不可直接相加。扩展的候选项见下文。

## 网页冷启动

### 下一张预设壁纸

`restoreWallpaper()` 在读取 IndexedDB 并发起当前壁纸渲染后完成，当前图此时可能仍在下载。桌面空闲任务随后用 `new Image()` 立即请求下一张。现有条件跳过自定义壁纸、宽度不超过 768 px、节流标记为 `2g` 或开启省流的场景。 [启动调度](../../src/js/init.js#L145) · [恢复和预载](../../src/js/modules/wallpaper.js#L460)

1440×900、DPR 2、4 倍 CPU 降速、120 ms 网络延迟、250 kB/s、首次资源缓存为空。每组四次交替。启用预取时，四次都在 `bg1.avif` 完成前发出 `bg2.avif` 请求。关闭后，`bg1.avif` 下载完成中位数从 4.63 秒降至 3.81 秒。当前图 `Image.decode()` 完成中位数从 4.67 秒降至 3.85 秒。前景 FCP 样本有重叠。

网页首装和第一次受 Service Worker 控制的导航还可能各下载一次 `bg2.avif`，因为当前构建的图片缓存首次未命中会以 `cache: 'reload'` 获取。测试中的第三次导航已命中缓存。优先在启动时移除这次推测请求，另测主动切换的等待时间。 [本地图片缓存](../../sw.js#L427)

### 导航图标预取

默认预取前五个分类。去掉与首页快捷书签重复的资源，它会额外请求 51 张书签 PNG，共 326,774 B。390×844、DPR 3、80 ms 延迟、250 kB/s、绕过 SW 与 HTTP 缓存时，每组交替测三次。第 6.5 秒首次切入，现状已有 288–293 kB 额外 PNG 完成传输。只预取第一个分类的版本完成了 109,716 B，两边进入后实际可见的 19 张图标都已加载。首次切屏时的图标激活继续按现有范围运行。 [预取与切入](../../src/js/modules/bookmarks.js#L189)

第 3 秒进入时，两边在切屏结束时都暂未加载可见图标，后续就绪时间波动。1920×1080 桌面可见 52 张，统一改成只预取第一组会让切屏结束时的就绪数从 38/52 降到 24–26/52。先针对窄屏缩减预取，验收保留快进场与桌面就绪情况。 [导航图标与侧栏测试](../../test/ui-nav-rendering.test.mjs#L5)

### Service Worker 首次安装

生产构建的 `./` 与 `./index.html` 由同一份 HTML 提供。基线安装使用 `cache: 'reload'` 下载两个入口及带构建指纹的 app。模拟部署缓存头、本地 Brotli 和 ETag 时，正常首访已下载 41,780 B HTML 和 43,241 B app，安装再传输 126,801 B 同内容资源。默认壁纸已有条件验证，本轮得到 304。

此项已实现。两条文档路由共用一个缓存项，安装时条件重验证 HTML、复用仍新鲜的 immutable app，并在响应校验失败时绕过 HTTP 缓存重试。生产构建复测中，从根路径首访只出现一次 HTML 304，额外核心正文降到 0 B。直接首访 `index.html` 时，仍可能因 HTTP 缓存键不同而下载一次根路径文档。Chrome 回归覆盖了失配重试、子目录的离线入口、升级与缓存恢复。 [安装](../../sw.js#L223) · [文档路由](../../sw.js#L320) · [升级回归](../../test/infra-sw-upgrade.test.mjs)

### 竖屏默认壁纸

默认图为 2560×1708，390×844 竖屏的 `cover` 只显示源图中央一部分。本地将源图居中裁为 1280×1708，按配置中的同等质量参数重新编码，保留源图垂直像素与居中取景。单图 409,689 → 205,815 B，减少约 50%。在 120 ms、250 kB/s、4 倍 CPU 降速的四次交替实验中，两组下载完成中位数为 3.75 → 1.77 秒，`Image.decode()` 完成为 3.89 → 1.80 秒，FCP 为 370 → 364 ms。两份窄屏截图取景相近。 [预设配置](../../src/js/config/backgrounds.js#L15) · [构建模板的预加载](../../src/index.html#L69) · [壁纸渲染](../../src/js/core/wallpaper-renderer.js#L137)

实验只替换了默认壁纸响应，应用仍使用原 URL。正式实现需让首屏预载与运行时恢复选择同一资源，保留设置中的壁纸身份，并验证横竖屏变化、高 DPR 锐度、初次离线可用性和 SW 缓存命中。可先量产默认图确认收益，再考虑其它预设。

## 交互与扩展

### 上传高分辨率本地壁纸

4096×2304、1.74 MB JPEG 通过真实文件输入上传，使用生产逻辑缩到 3840×2160，开启减弱动效以隔离编码。每组每档 CPU 三次。用 `canvas.toBlob()` 编码，再转成目前持久化的 Data URL，输出尺寸、质量和字节数相同。4 倍 CPU 降速时，同步调用从 155–227 ms 降到 25–96 ms，预览前遇到超过 50 ms 主线程任务的样本从 3/3 降到 1/3，最大 rAF 间隔从 183–267 ms 降到 50–100 ms。预览完成总耗时有重叠。重点验收取消、重新选图、保存和迟到的编码回调。 [上传实现](../../src/js/modules/wallpaper.js#L526) · [壁纸回归](../../test/data-wallpaper.test.mjs#L194)

### 大量书签的模糊搜索

当前对每个词的最多三个近似长度前缀分别计算完整编辑距离矩阵。原型在同一矩阵里计算这些前缀，只访问现有容错范围内的单元，并复用三行缓冲区。390×844、DPR 3、4 倍 CPU 降速下，每组 15 条常规查询各重复五次，通过 CDP 输入并测量从 `beforeinput` 到应用 `input` 处理返回的同步时长。 [编辑距离](../../src/js/utils/bookmark-search.js#L59) · [输入处理](../../src/js/modules/search.js#L551)

| 已保存书签数 | 常规查询 P95 | 62 字符无匹配粘贴 |
| :--- | :--- | :--- |
| 8（默认） | 4.4 → 3.5 ms |  |
| 48 | 10.1 → 4.3 ms |  |
| 250 | 26.1 → 7.8 ms | 114–117 → 3.5–4.3 ms |
| 1,000 | 85.7 → 19.9 ms | 458–492 → 10–13 ms |

大量书签场景使用合成的长 URL，测量范围为同步处理耗时。浏览器实验的候选 URL 与顺序逐条一致，另做了 3,273,453 组短词距离等价性对照。推进时复用现有搜索模型及联想回归，保留名称、地址、简介的优先级及拼写容错。 [排序测试](../../test/data-pure-models.test.mjs#L28) · [联想回归](../../test/data-request-performance.test.mjs)

### 移动导航渲染

默认空闲预热创建整个导航 DOM，但现有 `content-visibility: auto` 只在未预热而直接切屏时启用。关闭空闲预热使首页元素从 1,438 减到 533，同时让首次切入的首个 rAF 间隔达到 90–122 ms。对照将现有渲染延后规则用于空闲构建，并让规则在首次滚动时持续生效。390×844、DPR 3、4 倍 CPU 降速、每组四次的已预热复测中，切入后首个 100 ms 内最大样式重算 16.06–18.42 → 9.16–11.06 ms，首个 rAF 间隔 25.0–27.4 → 20.7–22.1 ms。桌面原速首个 rAF 仍约 16–17 ms。如果在第一轮离屏图标激活时撤销规则，部分成本会集中到第一次滚动。 [渲染入口](../../src/js/modules/bookmarks.js#L388) · [现有规则](../../src/styles/page.css#L742)

值得继续验证窄屏范围，覆盖首次滚动、侧栏定位、键盘焦点、页面内查找和滚动高度。紧贴启动的切屏仍观察到 GPU 长任务，有一例约 616 ms 的 rAF 间隔与约 612 ms 的 GPU 任务重合，现有数据只确认两者同窗出现。 [历史切屏追踪](2026-10-29-transition-audit.md#继续收敛资源渲染后端与真实后台恢复)

### 扩展头部脚本

把最前面连续的语言、构建指纹和浏览器标记脚本合成一个外置文件，保留其执行顺序、defer app 与 body 中的脚本位置。真实解包扩展 URL、关闭缓存、每组每档 13 次交替导航。阻塞 bootstrap 请求 9 → 7。原速 DOMContentLoaded 中位数 76 → 36.5 ms，FCP 112 → 116 ms。4 倍 CPU 降速时两项分别为 198.3 → 109.5 ms 和 188 → 140 ms。上线前在 Chrome 的新标签页入口复测，并验证深色底、保存主题、英文与离线打开。 [扩展构建](../../scripts/build-extension.cjs#L42) · [扩展回归](../../test/infra-chrome-extension.test.mjs)

## 暂缓的方向

- 单独把壁纸 preload 提前，慢网下确实让请求提前约 66 ms，但下载完成只提前约 43 ms，同时 FCP 慢约 36 ms。HTML 和主脚本分别约 41.8 kB、43.2 kB Brotli，优先减少资源本身和竞争请求。
- 热缓存 SW 的指纹读取改成先读响应前段，25 轮受控导航中，原速文档 worker 中位数 1.8 → 1.3 ms，FCP 中位数均为 92 ms。正常暖态后台返回的基线复核中，移动尺寸、CPU 4 倍降速，主页与导航页各 6 次真实标签页切换，`visibilitychange` 同步处理为 0.5–6.9 ms。当前证据不足以优先改这两条链路。
- 历史对照削减毛玻璃、蒙版或把切屏图片替换为 1×1 图，收益未稳定复现。历史报告确认的强制布局已有修复。 [切屏对照](2026-10-29-transition-audit.md#分离图片与装饰成本)

研究阶段完成了隔离的网页与 Chrome 扩展构建、上述 Chrome 对照和临时 SW 回归。实现 SW 首装优化后，`npm run lint`、`npm test`（135 项）和本地 Nu / Stylelint 校验均通过。
