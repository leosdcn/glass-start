# Safari 切屏性能对照：2026-10-23

本次验证 Chrome 切屏悬停修复在 Safari 中的表现。抽屉模式修复前后结果接近；经典模式重复切换总体接近，但修复后一次返回采到 70ms rAF 间隔，其余 9 次返回最大间隔均为 47–49ms。该异常保留在原始数据中，尚未定位原因。

新增 CSS 以 `html.is-chrome body.is-screen-transitioning` 为条件，Safari 实测该类不存在，原有过渡与玻璃策略继续生效。没有依据将本轮修改称为 Safari 加速。

## 环境和方法

- Safari 27.0.1（22625.1.29.11.28），macOS 27.0.1，MacBook Air，页面视口 1454 × 727 CSS px、DPR 2；没有 CPU 降速，减弱动效关闭。
- 修复前为 Git `8fef9fb`，生产构建 `app-core-v1792735964869`；修复后为该提交加切屏悬停 CSS 与回归测试，生产构建 `app-core-v1792739914302`。
- SafariDriver 建立会话超时后，改为原生 Safari 新标签页运行页面内采样器，没有更改 Safari 设置。使用 8 个独立本地端口作为新来源，隔离本地存储与 Service Worker；同一 Safari 进程逐页运行，不保证系统字体、网络或磁盘缓存全冷。
- 两种模式各按“修复前 → 修复后 → 修复后 → 修复前”运行。每页先等待应用、字体与 700ms 稳定期，并采样 30 个空闲帧；随后首次往返一次、重复往返五次，共 **96 次切屏**。
- 应用 JS 和样式直接来自生产产物；测试 HTML 内加入模式设置、固定天气数据、结果采集脚本，并限制外部脚本、连接和图片请求。两端采用相同测试包装，Service Worker 不控制页面。
- 使用仓库 `test/benchmark-transition.mjs` 的 `measureTransition`、`summarize` 和分位数算法。按方向键开始采样，等目标状态、切屏节点过渡结束及连续三帧稳定后结束，因此总时长包含收尾确认，不能当成 CSS 声明时长。
- 空闲 rAF 基准中位数为 17ms。以下均为主线程 **rAF 回调间隔**，不是 Safari 的 GPU/物理呈现帧时间，也不能与此前 Chrome 的 `SwapBuffers` 数字直接比较。

## 重复切换结果

单位 ms，箭头为修复前 → 修复后。每种条件每个方向各 10 次重复样本，排除首次进入和首次返回；P95 从该组全部原始回调间隔汇总计算。

| 模式与方向 | 采样总时长中位数 | rAF 间隔 P95 | rAF 最大间隔 |
| --- | ---: | ---: | ---: |
| 抽屉重复进入 | 565 → 566 | 30 → 31 | 49 → 50 |
| 抽屉重复返回 | 565 → 565 | 27 → 29 | 50 → 50 |
| 经典重复进入 | 617 → 618 | 31 → 33 | 50 → 50 |
| 经典重复返回 | 615 → 614 | 28 → 31 | 49 → 70 |

全部分组的 rAF 间隔中位数均为 17ms。抽屉重复切换没有超过 50ms 的间隔；经典修复后有一次重复返回出现两段超过 50ms 的间隔，最大 70ms，不能将这个最大值隐藏在平均数中。

## 首次切换结果

每组只有两个页面首次样本，以下列最大 rAF 间隔，保留冷启动长间隔。

| 模式与方向 | 最大 rAF 间隔（修复前 → 修复后，ms） |
| --- | ---: |
| 抽屉首次进入 | 106 → 109 |
| 抽屉首次返回 | 64 → 59 |
| 经典首次进入 | 102 → 84 |
| 经典首次返回 | 65 → 66 |

Safari 首次进入也存在主线程回调长间隔，本次没有测量实际呈现间隔，不能仅凭这些数值判定与用户观察到的画面流畅度矛盾。

## 功能核对与验证范围

96 次切换收尾时页面均可见且聚焦，切屏锁均解除。进入后导航可见、`inert=false`，玻璃表面计算值为 `blur(24px)`；返回后导航隐藏、`inert=true`，离屏玻璃计算值为 `none`，符合 Safari 原有策略。采样完成提示已通过 Safari 界面核对，随后关闭本次测试标签页，保留原有页面。

这只核对了状态与计算样式，没有另行完成闪白、背景穿透等逐帧视觉走查或 GPU 时间线采集；iOS/iPadOS、BFCache 与触控板手势不在本次采样范围。
